# Status-menu display input switching

Users connect a 27C1U-D to Mac USB-C and Windows HDMI. Both computers must be able to switch to the other input from T-Cube. The requested control has Type-C on the left and HDMI on the right. Retain existing UI appearance and commands.

## Validated hardware contract

2026-11-05 physical tests: Mac exact UUID verified locally, name27C1U-D, EDID vendor9699 (IOC), product65535 (FFFF). Type-C GetVCP0x60 returns7/max14; HDMI returns5/max14. Advertised standard HDMI17 does not work. Mac sending5 using the existing two-transmission transport actually switches to Windows. One transmission did not work. Windows Dxva2 SetVCPFeature0x60=7 switches to Mac; hardware interface IOCFFFF was matched uniquely. The other Windows monitor GWD0140/current16/max3 was untouched. After switching away, the originating host cannot read back. That is an expected unconfirmed result, not proof of failure. Follow-up controlled Windows test skipped inactive-source preflight and sent HDMI5 after switching to Type-C: API accepted the write, but the user confirmed the picture stayed on Mac and Windows readback remained unavailable. Thus inactive write-only recovery also failed on this unit. User explicitly chose local-host lightweight controls instead of authenticated LAN coordination; no force-write UI is included.

## Behavior and identity

User follow-up explicitly requests general monitor support. Use generic VCP0x60 transport with per-monitor, user-calibrated two-port mapping. Built-in known27C1U-D profile is an automatic default only when exact model identification is available (name + IOCFFFF on Mac; EDID descriptor from bounded registry read on Windows). Otherwise offer it explicitly as a preset, never infer model solely from generic IOCFFFF. Unknown supported-DDC displays can be configured with Type-C and HDMI raw decimal codes0...65535, which must differ. Show the freshly read current code so users can calibrate their active port; explain that the other code may need reading from its active host. Do not promise USB-C auto detection from generic MCCS or brute-force codes.

Persist a separate versioned display-inputs.json keyed by full stable display identity (UUID on Mac; full monitor interface on Windows). Validate all mappings and bounds. Atomic saves; malformed existing JSON stays intact and blocks save with actionable error, never silently replace it. Do not modify the existing launcher configuration schema. User mapping overrides known presets; unsupported/unknown active input disables switching until calibrated. Explicit save re-reads active input; no write during calibration. Offer reset only as a deliberate per-monitor mapping action if needed, not automatic.

macOS requires exact display UUID per operation. Windows must resolve physical handles afresh against full monitor interface identity, including physical-monitor index only where unambiguous; do not select by array order or generic name. Other displays receive no Set command until the user has configured that exact display. Reject ambiguous cloned physical targets.
macOS inserts a native two-tick NSSlider into the existing status menu. Windows adds a tray-menu item opening a small, themed, tray-anchored panel with a two-position range control. Preserve the current Windows tray left-click cube toggle. Show model/current source and loading, unsupported, busy, failure, sent-unconfirmed states. Only commit when the slider releases or a keyboard change commits; no writes while dragging. Disable during writes and when input/profile/identity is unknown. Same-source actions do nothing.

Opening reads once; explicit refresh re-reads. No background polling, startup writes, persistent source restoration or network coordination. Serialize DDC with brightness on macOS. Windows blocking calls execute in a lazy worker with bounded operations, fresh handle ownership and cleanup on every path. All privileged IPC must authorize exact panel webContents and main frame before validating narrow payloads. No generic arbitrary VCP API reaches renderers.

Each write checks a fresh readable active input on the exact target and writes the requested profile value once at the application level; native Mac transport uses its validated two transmissions. After a short bounded delay, valid matching readback means confirmed; valid unchanged reply means not applied; missing/invalid response after accepted write means sent-unconfirmed. Do not retry or revert after a switch, and do not falsely show requested input as confirmed. A failed preflight/read/transport stays a failure. Topology and close cancel queued work; an already-sent write can finish without UI resurrection.

Only the new, isolated display-inputs.json schema is added; existing user JSON schemas remain unchanged. Both apps can switch away from themselves; neither promises to reclaim an inactive input. Explain switching back from the active host or physical OSD. Power/brightness/volume and peripherals are outside scope.
